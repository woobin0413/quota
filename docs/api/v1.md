# Quota API v1

The interface between this web repo and the separate native iOS/Android repo.
Everything a mobile client is allowed to depend on is written here. Anything not
written here is an implementation detail and may change without a version bump.

Base URL: `https://sendquota.com/api/v1`

## Authentication

Auth0 Authorization Code + PKCE against a **Native** application. The app sends
the resulting access token as `Authorization: Bearer <token>` on every request.

- Auth0 domain: `AUTH0_DOMAIN` (custom domain `auth.sendquota.com`)
- Audience: `https://api.sendquota.com` — required, or the token comes back
  opaque and every call 401s
- Scopes: `openid profile email offline_access` — without `offline_access` no
  refresh token is issued and the app re-runs the full login every hour
- Callback / logout URL: `com.sendquota.app://callback` (the scheme is
  `AUTH0_MOBILE_SCHEME` on the provisioning side; the app must register it)
- Tokens are RS256 JWTs, verified offline against the tenant JWKS. Issuer
  `https://<AUTH0_DOMAIN>/`, audience as above, algorithm pinned to RS256 — a
  token that fails any of those is indistinguishable from a forged one and gets
  the same 401.

> **Authenticate against `auth.sendquota.com`, never the tenant domain.** The
> `iss` claim is a property of the host that minted the token, not of the
> tenant: the same client and the same audience yield
> `https://auth.sendquota.com/` through the custom domain and
> `https://dev-….us.auth0.com/` through the tenant domain. The API pins the
> former, so a token minted against the tenant domain fails the issuer check and
> returns **401 `UNAUTHORIZED`** — with a signature, audience, algorithm and
> expiry that are all perfectly valid. It reads as a credential bug and is a
> configuration one. This was hit for real during the first end-to-end test of
> this path. (The Management API is the exception and stays on the tenant
> domain — that is why `AUTH0_MGMT_DOMAIN` exists — but no mobile client should
> ever touch it.)

**Verified end to end.** `e2e/mobile-bearer.spec.ts` runs the real chain against
the live tenant: authorization-code + PKCE login, claim injection, `/me` at 200,
then a **refresh exchange** whose new access token still carries both claims.
That last assertion is the load-bearing one — access tokens live an hour and
refresh tokens thirty days, so nearly every token this API sees comes from a
refresh, and claims that did not survive it would 403 every session at exactly
the one-hour mark. Keep that spec green.

**Custom claims.** An access token minted for a custom API carries only the
OIDC-registered claims — no `email`, no `email_verified`. A post-login Action
adds them, **namespaced**, because Auth0 silently drops custom claims that are
not URIs:

- `https://sendquota.com/email`
- `https://sendquota.com/email_verified` (boolean; compared with strict
  equality, so the string `"false"` does not pass)

Verification **fails closed**. If the Action is not deployed, `email_verified`
is absent, and every mobile user is held at the 403 email-verification gate
rather than waved through.

**Token lifetimes.** Access token **1 hour** (`token_lifetime: 3600` on the
resource server). It is verified offline against JWKS, so there is no revocation
path — the lifetime *is* the exposure window for a token lifted off a device or
read out of a debug proxy.

Refresh token: **rotating and expiring** — `rotation_type: "rotating"`,
`expiration_type: "expiring"`, **30-day** absolute ceiling (2 592 000 s),
**15-day** idle ceiling (1 296 000 s), **30 s** rotation leeway. Rotation is
what makes revocation possible at all, and it gives reuse detection for free:
replaying a spent refresh token makes Auth0 revoke the whole family, cutting off
the thief and the real device together. That simultaneous logout is the intended
signal, not a bug — treat it as a credential-compromise event, not as something
to engineer around.

Run one refresh at a time. Two concurrent refreshes race, and the loser's replay
looks like token theft, which revokes the family and logs the user out.

Store the refresh token in the platform keystore — iOS Keychain, Android
Keystore. Never `AsyncStorage`, `UserDefaults`, or `SharedPreferences`.

There is no API key, no shared secret, and no separate mobile login. Identity is
the same Auth0 user as the web app: one account, both clients. The native app is
a **public client** — its client id is in the binary and is not a secret; PKCE,
not the client id, is what secures the exchange.

**A bearer token wins outright over any other credential.** If a request carries
an `Authorization: Bearer` header, that token *is* the identity: an invalid one
is rejected rather than falling back to anything else. A bearer token aimed at a
non-`/api` path also gets a JSON 401 rather than an HTML login redirect, so a
misconfigured client gets something it can act on.

**No CORS headers are served, deliberately.** Native HTTP clients send no
`Origin` and are not subject to the same-origin policy, so they need none. A
browser page on another host therefore cannot call this API, which is the
intended outcome: the only browser client is the same-origin web app. Do not
build anything that depends on a preflight succeeding — there is no `OPTIONS`
handler either.

## Error shape

Every JSON error carries `success: false` and a stable `code`. **Branch on
`code`, never on the human-readable string** — copy changes without notice.

The human string is `message` on almost every route. Two exceptions carry it as
`error` instead: **every** failure from `POST /send-quote`, and the middleware
write-limiter 429. Read `message ?? error`, and treat neither as branchable.

### Codes a client must handle

| Status | `code` | Meaning |
|---|---|---|
| 401 | `UNAUTHORIZED` | Missing, malformed, expired, or wrong-audience token. Refresh, then re-login. |
| 403 | `EMAIL_NOT_VERIFIED` | Account exists but the email is unconfirmed. Call `POST /api/auth/resend-verification` (unversioned path — it is exempt from this gate). |
| 403 | `QUOTE_LIMIT` | Monthly quote cap reached. Body also carries `tier` and `limit`. Do not offer an in-app upgrade — deep-link to `subscription.manageUrl`. |
| 403 | `EMAIL_REQUIRES_PRO` | Free tier attempted an email send (`/send-quote` or a receipt). Offer the PDF instead. |
| 403 | `BILLING_REQUIRED` | `PATCH /subscription` outside dev. Plan changes go through billing on the web. |
| 400 | `INVALID_JSON` | Body was not JSON. |
| 422 | `VALIDATION_ERROR` | Body failed schema validation. `errors[]` carries `{ field, message }`. |
| 422 | `SCHEDULE_INVALID` | `PUT /quotes/{id}/milestones`: the schedule does not add up. `details[]` carries `{ path, message }`. |
| 404 | `NOT_FOUND` | Quote, payment, work item, or profile row not found — or owned by someone else. Ownership failures are deliberately indistinguishable from absence. |
| 429 | `RATE_LIMIT_EXCEEDED` | A limiter fired. Honour `Retry-After`; never retry in a tight loop. |
| 500 | `INTERNAL_ERROR` | Retry with backoff. |

### Validation is not uniform — read this before writing a client

Most routes use the shared validator: **`INVALID_JSON` 400**, then
**`VALIDATION_ERROR` 422** with `errors: [{ field, message }]`. That covers
`POST /quotes`, `PATCH /quotes/{id}`, `POST /quotes/{id}/payments`,
`PUT /quotes/{id}/milestones`, `POST /work-items`, `PATCH /work-items/{id}`,
`POST /work-items/import`, `PATCH /profile`, `PATCH /subscription`.

Two routes predate it and differ. They are frozen this way for v1:

- `POST /send-quote` — `VALIDATION_ERROR` at **400**, not 422, and the list is
  `details: [{ path, message }]`, not `errors: [{ field, message }]`. It also
  emits `INVALID_REQUEST` and `INVALID_EMAIL` (400), `QUOTE_NOT_FOUND` (404),
  **`INVALID_QUOTE_STATUS` (409 — the quote is already paid; send a receipt
  instead)**, `DATA_ERROR` (422, `details: [{ path, message }]`), and
  `EMAIL_SEND_FAILED` (500).
- `GET /quotes` — bad `limit`/`offset`/`search` query params return
  `VALIDATION_ERROR` at **400** with no `errors` array at all.

So: **do not key on the status code alone.** Treat 400 and 422 together as
"client sent something bad", and read `code`.

`POST /quotes/{id}/payments/{paymentId}/receipt` adds `NO_RECIPIENT` (400) when
the quote has no recipient email on file, plus `DATA_ERROR` (422) and
`EMAIL_SEND_FAILED` (500).

`POST /api/auth/resend-verification` uses **`RATE_LIMITED`** (429, no
`Retry-After` header) rather than `RATE_LIMIT_EXCEEDED`, and `RESEND_FAILED`
(502) when Auth0 will not send.

### The 401 body, and a split to leave alone

A native client always receives:

```json
{ "success": false, "code": "UNAUTHORIZED", "message": "Authentication required" }
```

— from the middleware bearer gate and from every route handler alike,
deliberately, so a rejected credential looks the same wherever it was rejected.
(`/send-quote`'s own 401 spells the string `error` rather than `message`, per the
note above; `code` is identical.) In practice the gate answers first: a missing
or invalid token never reaches a handler.

The **cookie**-authenticated web path still returns a bare
`{ "error": "Unauthorized" }` from middleware. That is not an oversight and it
is not the mobile contract: the running web app already consumes that shape.
**Do not "harmonize" the two by changing the cookie path** — every client-side
fetch that inspects an error body would need auditing first. Bearer had no
deployed clients when the split was made, which is exactly why the bearer side
was the one free to change.

The 403 verification body is:

```json
{
  "success": false,
  "code": "EMAIL_NOT_VERIFIED",
  "message": "Confirm your email address to finish setting up your account."
}
```

## Rate limits

Keyed on the **authenticated Auth0 `sub`**, never on IP — behind mobile carrier
NAT thousands of users share one address, and IP keying would throttle a region
off one abuser. The same subject gets one budget whether it presents a bearer
token or a session cookie.

| Scope | Budget | Applies to |
|---|---|---|
| Write budget (middleware) | **60 writes / 60 s** | `POST`, `PUT`, `PATCH`, `DELETE` on any `/api` path except those below |
| `/send-quote` | 10 / 60 s | its own limiter |
| `…/payments/{paymentId}/receipt` | 10 / 60 s | its own limiter |
| `/api/auth/resend-verification` | 3 / 60 s | its own limiter, `code: "RATE_LIMITED"` |
| `/api/billing/*` | 10 / 60 s | not exposed to mobile |

**Reads are never rate limited.** Only the four write methods draw from the
write budget.

`/api/v1/x` and `/api/x` are the same endpoint and **share one budget** — moving
a client to the versioned path does not buy it a second allowance.

429 bodies are not identical, so read the header rather than the body:

- write limiter and `/send-quote` — `Retry-After`, `X-RateLimit-Limit`,
  `X-RateLimit-Remaining`, `X-RateLimit-Reset`, plus a `retryAfter` field
  (seconds) in the body
- receipt send — `Retry-After` only, no `X-RateLimit-*`, no `retryAfter` field
- `resend-verification` — no headers at all; back off a minute

`Retry-After` (seconds) is present on every 429 except `resend-verification`.

The write limiter is **in-memory and per-instance**. Vercel runs middleware in
several ephemeral instances per region, so the effective ceiling is a multiple
of 60/min and a burst may pass. Treat the limit as the contract and the extra
headroom as luck — it is a speed bump against scripted abuse, not a guarantee.
A client that queues offline writes and flushes them all on reconnect will walk
straight into this; pace the flush.

## Endpoints

Relative to `https://sendquota.com/api/v1`. The listed methods are exhaustive —
anything else is a 405. Every path except `/me` is a thin re-export of the web
app's own handler, and a parity test asserts each one exposes exactly the
methods that handler defines.

| Path | Methods | Notes |
|---|---|---|
| `/me` | GET | Session bootstrap: profile, tier, monthly quota usage |
| `/quotes` | GET, POST | List (`limit`, `offset`, `search` query params) / create |
| `/quotes/{id}` | PATCH | Internal notes |
| `/quotes/{id}/pdf` | GET | `application/pdf` bytes, `Content-Disposition: attachment`. Watermarked on Free, logo on Pro+ |
| `/quotes/{id}/payments` | GET, POST | Payment history / record a payment |
| `/quotes/{id}/payments/{paymentId}` | DELETE | Remove a recorded payment |
| `/quotes/{id}/payments/{paymentId}/receipt` | POST | Email a receipt (Pro+) |
| `/quotes/{id}/milestones` | GET, PUT | Deposit / progress schedule |
| `/work-items` | GET, POST | Catalog |
| `/work-items/{id}` | PATCH, DELETE | Update / soft-deactivate |
| `/work-items/import` | POST | Import starter templates by trade |
| `/clients` | GET | Contacts with their quotes. Paged — see the ceilings below |
| `/send-quote` | POST | Email the quote + PDF (Pro+) |
| `/subscription` | GET, PATCH | GET: tier and usage. **PATCH is a dev-only tier switch and returns 403 `BILLING_REQUIRED` in production** — it exists only because the handler is re-exported whole |
| `/profile` | GET, PATCH | Business name and contact details |

One unversioned path is part of the mobile contract:
`POST /api/auth/resend-verification`. It is not under `/api/v1` because it is
shared with the web app, and it is the only route reachable while the account is
held at the `EMAIL_NOT_VERIFIED` gate.

### `GET /me`

The one endpoint with no web equivalent — the web app gets this from Server
Components, which a native client cannot render. Everything needed before the
first render, in one call:

```json
{
  "success": true,
  "user": {
    "id": "uuid",
    "email": "contractor@example.com",
    "firstName": null,
    "lastName": null,
    "companyName": null
  },
  "subscription": {
    "tier": "free",
    "quoteLimit": 3,
    "quotesUsed": 1,
    "manageUrl": "https://sendquota.com/billing"
  }
}
```

- `tier` is one of `free` | `pro` | `ultimate`. An unrecognized stored value
  resolves to `free`, never to unlimited.
- `quoteLimit` is `3` (Free), `15` (Pro), or **`null` for unlimited** — Infinity
  is not representable in JSON. Treat `null` as no cap, not as zero.
- `quotesUsed` counts quotes created in the current **calendar month, UTC**. The
  same quantity is published under the same name by `GET /subscription`; there
  is exactly one name for it.
- `firstName`, `lastName`, and `companyName` are **null for a fresh account**.
  Auth0 database signups yield an email and nothing else, so the app must prompt
  for a business name before the contractor's first invoice goes out headed by a
  raw email address.
- `manageUrl` is where a client sends users for anything billing-shaped.

## `/clients` has two ceilings — read both before rendering a list

`GET /clients` returns contacts with their quotes joined. It takes `limit`
(1–200, default **200**) and `offset` (default 0), and answers with:

```json
{
  "success": true,
  "clients": [ /* … */ ],
  "pagination": { "total": 340, "limit": 200, "offset": 0, "hasMore": true },
  "quotesTruncated": false
}
```

**`pagination.hasMore`** — there are more contacts than this page. Page with
`offset`, or tell the user the list is partial. Do not assume `clients` is
everything: the default page is 200 and a busy contractor can exceed that.

**`quotesTruncated`** — a different and nastier condition. Quotes are fetched in
a single query (ceiling 500) and joined to contacts in memory, which keeps the
endpoint at two queries instead of N+1. When that ceiling is hit, **some
contact's `quotes` array is short** — and nothing about that contact looks wrong.
Paging with `offset` does not fix it, because the quote query is not scoped to
the page. When this is `true`, either fetch a contact's quotes individually or
tell the user the history is partial. Rendering it as complete shows a
contractor the wrong record of who owes them money.

Both fields are additive and were introduced after the endpoint already
truncated silently — the old behaviour is the default (`limit=200, offset=0`),
so nothing changed for existing callers except that the truncation is now
visible.

## Not exposed, deliberately

- **`/api/billing/*`.** Card entry is Stripe Elements, which is web-only, and
  selling a digital subscription inside an iOS binary is an App Store policy
  question rather than a technical one. The app reads tier from `/me` and sends
  users to `subscription.manageUrl` to change plans.
- **`PATCH /api/subscription` as a real capability.** The method is reachable
  (it rides along with the re-exported handler) but it is a dev/e2e tier switch
  guarded by `ALLOW_DEV_TIER_SWITCH`, which is never set in production. In
  production it returns 403 `BILLING_REQUIRED`. Do not build against it.
- **`/api/profile/logo`.** Multipart upload used by the web settings screen; not
  versioned, not part of this contract.
- **`/api/webhooks/*`, `/api/cron/*`.** Server-to-server, separately
  authenticated.
- **Any paid/unpaid toggle.** There is none. A quote's `is_paid` is derived by a
  database trigger from the payments recorded against it, so the way to mark a
  quote paid is `POST /quotes/{id}/payments`.

## Versioning policy

`/api/v1/*` paths are frozen. A shipped App Store binary cannot be
force-updated, so an old version is calling these paths for as long as it exists
on a device.

**Allowed** without a version bump:

- adding a new endpoint
- adding a new optional request field
- adding a new response field

**Requires `/api/v2`:**

- removing or renaming any request or response field
- changing a field's type or its null semantics
- changing a status code or a `code` value
- making an optional request field required
- removing a method from an existing path

The v1 files in `app/api/v1/` re-export the base handlers in `app/api/`, so
editing a base handler edits v1 — there is no second copy to forget and no drift
between them. The parity test in `app/api/v1/__tests__/parity.test.ts` catches a
method appearing or disappearing, asserts the v1 module re-exports the identical
function rather than a copy, and compares Next.js route-segment config (which is
**not** inherited through a re-export — an uncopied `dynamic = "force-dynamic"`
would quietly make an authenticated response cacheable). What it cannot catch is
a renamed response field. That one is on review.

## Repository split

- **This repo** owns the API, the database, PDF generation, email, and Stripe.
- **The mobile repo** owns the native app and consumes only `/api/v1` (plus the
  one unversioned resend-verification path).
- **No shared code package exists today.** The types live in this repo's
  `types/` directory and are not published anywhere; the mobile repo writes or
  generates its own models against this document. Publishing them as a package
  is the intended fix if drift becomes painful, but a monorepo is not — the
  native toolchain has no overlap with the Next.js build, and one repo would run
  both CI pipelines on every push.
